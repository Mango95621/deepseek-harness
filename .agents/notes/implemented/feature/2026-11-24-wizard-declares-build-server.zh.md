# Agent Note: 引导向导经拥有记录的领域服务声明编译服务器

Status: implemented

[English](2026-11-24-wizard-declares-build-server.md) | 中文

## 问题

向导第四步列出项目已声明的编译服务器，并给出两条离开该步的路——"暂不配置服务器"与"下一步"——而两者调用的是同一个完成动作。这张卡片等于请操作者去找一个并不存在的差别，而真正点出该步问题的那个按钮，读起来却像是逃生出口。

什么都没声明的操作者在该步无法声明任何东西。文案让他在对话里请智能体调用 `remote_server_declare`——可对话正是门禁扣住的那层界面，工具也正是经它才能到达。一次引导里，第四个问题只能靠离开这次引导才能回答，那它就不是引导。

`@deepseek-ai/dsh-yxspec-api` 曾把该步记为只读："能以 UI 直接写入声明的实现，会成为通往持久状态的第二条未经校验的路径。"这一判断指着真实的危险——客户端自行构造记录的写入方——但由此并不能推出向导不得声明，只能推出声明的写入必须走那条会校验它的路径。

## 决策

`yxspecRemote.declareServer(workspaceId, draft)` 接受浏览器提交的声明，并转交 `ctx.yxspecRemote.declare`，即 `remote_server_declare` 工具所用的同一个服务方法。一个服务方法、两扇前门：记录的类型、校验与持久写入都留在 `@deepseek-ai/dsh-yxspec-remote`，任一扇门都不会接受另一扇拒绝的声明。对"一条路径"的另一种读法——控制器重新实现 `validateServer`——会造出两份可能不一致的校验，而那正是原先那份判断要防的失效。

草稿是与服务自身服务器接口不同的线上类型，差别只有一处：`recipes` 在线上是有序列表，在记录里是按 id 索引的映射。填它的表单是一列行，而映射没有地方安放重复的 id——第二行会静默覆盖第一行，而两行都还在屏幕上。该转换由 `declareServer` 完成；可选字段则由宿主而非表单解析：空名称取 id、省略的超时取 900000 毫秒默认值、recipe 的空 `outputDirectory` 保持缺省（于是每次运行按 recipe 解析默认值，而不是把一份会过期的副本存进记录）、空 `sshExecutable` 保持缺省、重复的 recipe id 保留最后一条命令——每一条都与工具路径既有行为一致。把这些解析集中在一处，才使向导与工具对"未指定的字段"含义一致。

两种失败是带类型的，而不是静默的，因为无处落地的写入不能看起来像已经落地。`yxspecRemote/service-unavailable` 报告该部署未挂载编译服务器服务；`yxspecRemote/rejected` 携带服务自身的消息，向导把它渲染在仍然打开的表单之上，操作者据此改正宿主点名的那个字段，而不必重填整份声明。`servers` 保持相反的行为——seam 缺失读作"未声明"——因为找不到东西的读取可以说出来，而操作者刚填完的表单不可以。

向导该步承载表单，前进只有一个控件，其文案跟随状态：未声明任何服务器时为"暂不配置服务器"，已声明后为"下一步"。两种情况下"不声明就继续"都是同一个动作，状态改变的只有文案。每次写入后，该步从宿主读回清单，而不是把刚输入的内容追加到列表上，因此用同一个 id 重新声明会替换原有行；摘要步同样读回声明，因为照抄表单的确认会确认一台宿主未必持有的服务器。

推进 ASPICE 指针仍是经门禁的一次工具调用。声明不是流程步骤——它描述项目在哪里编译，不是某个阶段的证据——而 `yxspec` 命名空间依然不提供任何写入。这套界面上的第二个写入是连接测试的结论：`probeServer` 调用这条 seam 既有的探测，并把结果存到声明上，因此之后渲染出的列表描述的是最近一次尝试而非最近一次成功。该步骤在声明落地后立刻测试一次，并在每一行提供测试控件；状态从宿主读回，因此刷新与换浏览器得到的答案一致。

连接是两个字段而不是一个 destination：操作者填自己以谁的身份登录、要连哪台机器，表单把它们拼成记录与服务所取的 OpenSSH 目标。让人手拼 `user@host`，等于要求他为一件自己并不在运行的工具把语法写对；而只有一半（有用户名没主机）会被拒绝，而不是被发出去。

编译工程目录是"选"出来的而非"打"出来的：`browseServer` 用与运行同一个 SSH 客户端列出目录，从登录目录开始，操作者点着往下走。手打这一项正是操作者最容易填错的地方——浏览用的共享路径与那台机器看到的路径是两个字符串——而先连接一次同时解决两个问题：验证 destination 的连接，也正是能展示对面有什么的连接。列目录不是状态：在声明写入之前，什么都不落库。

## 曾考虑的替代方案

**保持该步只读，继续指向工具。** 这正是"问题"一节描述的现状：门禁扣住了对话，于是这条指引把操作者赶出引导，只为一个它自己的五个问题之一。它也留下了双按钮问题，因为两个控件仍会以完全相同的方式完成该步。

**让客户端直接写入持久记录。** 控制器要自行构造记录，并在浏览器里重复 `validateServer`，或者干脆省略它；持久表的 zod schema 是最后一道防线，它会把填错的声明报成存储故障，而不是报成一个待改的字段。

**让向导改为把预填的提示词送进对话，而不写入。** 为一个操作者正看着的表单搭一次模型往返，而且它需要一个门禁刻意扣住的会话——与"工具不能充当答案"是同一个理由。

**让 `declareServer` 直接接收服务自身的服务器接口。** 无需转换、无需第二个类型——代价是线上出现 recipe 映射，于是表单渲染的行序丢失，操作者输入的重复 id 也被藏起来。

**在该步探测服务器，让"已声明"意味着"可达"。** 可达性需要凭据路径与一次网络往返；而向导记录的是"已作答"而非"可达"，这正是空白首页首次绘制不必等待网络的原因。唯一必须抵达服务器的是运行本身。

## 后果

- `yxspecRemote` 命名空间不再一致地只读。包 README 记下这唯一的写入是什么、以及它为何不是流程步骤，以免旧理由被照原样恢复。
- 向导里做的声明与智能体做的声明在记录里无法区分：同一张表、同一个键、同一组字段，而且没有作者——记录只带 `declaredAt`，不带是谁写的。同一个服务方法的"两扇前门"，正是让这一点成立而不是一种期望的原因。
- 向导现在可以产出一次运行都不曾使用过的声明。该步文案说服务器会编译推送的源码；只有 `remote_build` 能证明它确实如此，而摘要步的服务器行报告的是"已声明"，不是"已被证实"。
- 该步的声明列表、摘要行与表单文案都归各语言字典所有：八份字典新增了字符串，包括占位符与字段标签，因此翻译向导的部署会把表单一并翻译。
