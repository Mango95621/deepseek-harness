# Agent Note: 远程编译在服务器已有的检出目录内执行

Status: implemented

[English](2026-11-24-remote-build-runs-in-place.md) | 中文

## 问题

远程编译 seam（`@deepseek-ai/dsh-yxspec-remote`）最初的原则是"服务器只是编译农场，绝不是记录之源"：一次运行把本地项目树打包、流式送入声明的基础目录下按项目划分的暂存目录、在解出的副本里运行配方，并把归档的 SHA-256 记为这次运行的输入身份。这套模型恰好在它本应服务的项目上不可用。车机源码树动辄数百 GB；每次编译前都要打包、经 SSH 推送、再解包，成本高于编译本身；而让它勉强可用的那些排除项（`.git`、`out`、`build`）恰恰是增量编译所必需的目录——于是每次运行都为开发者机器上本就存在的树付全价，而它产出的编译又是从冷输出开始的。

操作者的真实处境与模型假设相反：构建机上已经有检出目录，由团队自己的同步或 CI 保持最新；缺的能力是"到那台机器上、在那棵树里，跑我声明的命令，并把结果带回来"。

## 决策

声明点名服务器上的目录，而不再点名一个暂存根：

- `projectDirectory`（必填，绝对路径）——一次运行执行的检出目录。运行会 `cd` 进去并运行配方。harness 从不创建、替换或删除它；目录不存在是一次以点名路径失败的运行，而不是由 seam 造出来的目录：它自己建出的空目录等于一次什么都没编译的编译。
- `outputDirectory`（可选，绝对路径，**按 recipe**）——该条 recipe 的产物落地目录；recipe 省略时每次运行解析为 `<projectDirectory>/out`。它属于 recipe 而不属于服务器，因为同一棵树的整编与局部编译产物落在不同位置：Android 树的整编写入 `out/` 根，而单模块编译写入该模块自己的输出，一台机器一个目录只能描述其中之一。配方经 `{out}` 令牌拿到它，因为重定向产物（`OUT_DIR_COMMON_BASE`、`--output` 参数）是构建系统的决定，seam 的职责只是把这个位置命名出来；取回时路径按实际执行的那条 recipe 的目录解析。
- `captureRevision`（可选，默认关闭）——每次运行前读取服务端源码版本（树里有 `.repo` 时用 `repo manifest -r`，否则 `git rev-parse HEAD`），并作为这次运行的输入身份记录：单行且短时原样记录，同时始终记录完整输出的 SHA-256。之所以可选，是因为 `repo` manifest 会遍历整棵树的每个项目，而自带版本记录脚本的流程会为同一个问题付两次代价。读取失败绝不使编译失败：`revisionError` 说明原因，退出码仍是编译的裁决。

在版本读取与配方之间，运行会取回调用方点名的内容：`fetch` 是相对产物目录的一组路径，`fetchInto` 是它们的本地落点（在按次运行的子目录下）。服务在传输开始前就拒绝绝对路径、`~` 与任何 `..` 成分，因此取回产物不会变成读取构建机上任意文件的手段；缺少 `fetchInto` 时它直接拒绝，而不是自行编造一个落点。归档在 `fetchMaxBytes` 之下边写边受约束，传输过程中即被中止，因为误写整棵产物树只差一次按键。传输失败按请求的路径逐条报告，绝不抛异常：编译已经发生，而"产物是否到达"与退出码是两件独立的事实。

配置随模型一同收缩：`excludes` 与 `pushSource` 消失，`tarExecutable` 现在指用于**展开**取回归档的工具，新增的唯一旋钮是 `fetchMaxBytes`（512 MiB）。服务不再注入 `workspaceRegistry`，因为它根本不读本地项目；`paths.ts` 随 `projectSlug` 一起删除：不再有任何东西由项目标题推导服务端路径。

持久记录随之迁移。`remoteServerRecord` 用 `projectDirectory` 取代 `baseDirectory`、新增 `captureRevision`，其 recipe 映射也从裸命令字符串变为 `{ command, outputDirectory? }`；`remoteRunRecord` 用 `revision`/`revisionDigest`/`revisionError` 取代上传归档的 `treeDigest`，并开始存储命令行与两个目录。存储域升到 `version: 2` 且不列 `compatibleVersions`：两种形状没有任何字段含义相同，因此版本 1 的行是被拒绝而不是被当作版本 2 读取——让操作者重新声明一次，比让他的服务器悄悄开始在 harness 过去填写的目录里编译要好。

## 曾考虑的替代方案

**保留上传用于小树，另加就地模式作为第二种模式。** 一条 seam 里放两套模型、按声明选择：工具、持久记录、向导表单与每份文档都要同时承载两者，而 AOSP 这个场景恰好是随包发布的那份副本覆盖不到的。上传那一侧的存在意义是让**输入可证**（归档摘要）；就地模式用一个源码版本替代它，对一棵本就在那里的树，这是同一个事实。两者并存意味着为了一个"只存在于开发者机器上的树"保留较弱的机制——而这个场景按 seam 自己的判断就不值得复制。

**改为增量同步而非整树复制。** `rsync` 式的差量传输能让大树的上传变得可负担。它同时把服务端的树变成 harness 拥有、必须自行协调的**派生**副本，而这种归属正是这条 seam 刻意回避的：树归操作者所有，运行就不可能破坏开发者正在工作的东西，也无人需要决定差量中断后该怎么办。

**就着工作区已挂载的共享盘编译。** 基线检出在开发者机器上可通过 SMB 共享访问，因此完全可以不走 SSH、直接对着那个路径编译。它要求被挂载的文件系统就是一台能编译的机器（事实并非如此——工具链在 Linux 主机上），而且会把这条 seam 绑定到某一个部署的挂载布局上。

**无条件自动记录源码版本。** 每次都记录会让所有运行的记录天然可比，无需任何人选择。代价是每次运行前遍历一棵 `repo` 管理的树，并重复某些项目自己脚本已经产出的追溯信息；这个开关属于操作者，而 `revisionError` 让读取失败可见而非静默。

**产物改经共享文件系统回传，而不是 fetch。** 构建机导出了挂载的部署可以直接把产物丢过去。这假定挂载存在且对构建用户可写，并且让"带回了什么"在运行记录里不可见；而 fetch 点名路径、约束体积、报告到达结果。

## 后果

- **不再有归档摘要。** 输入身份是源码版本，且仅在声明要求时才有。需要可证输入又不想开 `captureRevision` 的项目，必须由配方自己产出可追溯的版本证据。
- **树的新鲜度成了部署自己的问题。** 运行编译的是 `projectDirectory` 处当时的内容，没有任何机制提示操作者它是陈旧的。陈旧的树编译出陈旧的源码，而记录下来的源码版本让这一点在事后可见——而不是事前。
- **构建机必须持有那棵树，且维持它不在这条 seam 的范围内。** 这是任何采用它的部署都要接受的真实前提，也正是 README 的"何时选用"现在坦白说明这一点、而不再描述上传的原因。
- **只有点名索要时产物才回来。** 这条 seam 自己不列目录，因此发现产物名属于配方或编译日志的职责。想要清单的调用方必须先知道它，或从日志里读出来。
- **台账比过去承载更多**——命令行与两个目录都被存储——因为没有归档摘要之后，记录的价值在于说清"在哪里跑了什么"，而不只是"针对哪份输入跑的"。
- **向导的服务器表单声明新字段**——编译工程目录、每行 recipe 各自的产物目录，以及版本记录开关——因此浏览器里做的声明与智能体做的声明形状一致，并且经由同一个服务方法。
