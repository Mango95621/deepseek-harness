# @deepseek-ai/dsh-client-ui-yxspec

[English](README.md) | 中文

## 概述

用 `dsh-client-ui-yxspec` 把流程摆到操作者面前：一个会话面板分区，列出每个已声明 ASPICE 阶段（步骤数、❄ 标记、声明的输入是否已落盘）与项目的构建服务器及其最近一次连接测试结论；另有引导向导，在项目、代码库、规格与构建服务器都确定之前保持空白会话关闭。凡 Web bundle，都应与发布其所读状态的 Remote owner 一同挂载。该分区不能推进任何步骤——那始终是经宿主门禁的一次工具调用——"测试连接"是它唯一的控件。

<a id="use-this-package"></a>
## 使用本包

在浏览器需要展示流程的地方挂载它；分区与向导会一并装载。

### 何时选用

凡操作者需要跟随受控流程的 Web 部署都应选用它，因为向导正是"在能够输入提示词之前先告诉操作者宿主期望什么"的东西——从一次失败的工具调用里才发现缺哪些输入，是把流程倒置。完全由命令行驱动的部署两个界面都不需要。两者只在名义上彼此独立：本包总是同时装载二者，因为正是这道门让分区的流程模型有意义。

### 最小配置

```yaml
- name: '@deepseek-ai/dsh-client-ui-yxspec'
```

| 字段 | 默认值 | 含义 |
|---|---|---|
| （无） | — | 本包不声明任何 `Config` 字段 |

本包不声明 `Config`：它门控哪个项目、读取哪些命名空间，都在渲染时从客户端上下文解析，而非来自某条组合配置。

### 引导的五个前置条件

面板这一节解析项目的方式与向导相同——从工作区与会话目录中、按操作者正在看的那个会话解析——因为面板的 owner share 不携带项目，而把项目穿过其他每一节的 props 是本包强加给邻居的成本。它的服务器清单是对 `yxspecRemote` 命名空间的第二次读取，因此未挂载该插件的部署仍能显示流程；连接测试按服务器逐个提供，因为只能由向导刷新的状态，恰恰会在会话成为提问方时过期。

向导按固定清单依次走过——`project`、`repositories`、`specification`、`server`、`ready`——顺序由数据决定：规格候选是项目自身代码库里的文件，因此在声明代码库之前没有任何可枚举的东西。完成状态按项目记录在浏览器存储中而非全局，因此同一浏览器里的第二个项目不会被第一个项目的答案门控。

前两步按"宿主在各时点能回答什么"划分职责。第一步是项目*诞生之处*：操作者只提供名称、不选目录，向导即创建一个无目录的项目——这是宿主本身建模的一种状态，而非残缺状态。第二步再逐个把代码库挂到该项目上，每次选择都是针对该项目的一条持久 `addRoot` 命令，而不是写进草稿、等后续 create 一并携带的条目。追加正是"第一个目录成为主根"的机制：追加到无根项目的根落在下标 0，无需任何提升动作即成为会话工作目录；而 `addRoot` 从不提升，因此再加第二个代码库不会把工作目录挪到操作者脚下。

无目录的项目没有任何路径可供宿主的幂等 `create` 匹配，因此事后无法按路径找回。向导于是把第一步收到的 id 记在它自己的持久槽（`yxspec-onboarding-target`）中，并优先于会话与工作区目录解析它——否则本次引导会丢掉那个亲手创建项目的步骤，而一次重载还会静默地再建一个。已不再注册的 target 会退回到目录规则，而不会去门控一个已不存在的项目。

第三步给出两条出路，因为规范文档常常在项目搭好之后才交付：从候选中挑一份，或用该步骤的"暂不选择规范文档"记录 `specificationDeferred`。两者都算答过该步——门禁照常放行——而路线条可以把它重新打开，因此之后选中的文档会取代这次推迟（反之亦然：一条同时声称两者的记录，等于声称了一份没人选过的规范）。

第三步还让操作者可以扩大检索范围。规格树常常与代码库并列而非在其内部——一个共享文档目录、一个交付包、一个流程输入归档——而项目布局里没有任何东西为它命名，因此宿主的自身遍历够不到它。该步骤的"添加检索目录"控件可挑选一个，这些添加项记在项目进度记录的 `searchPaths` 上，随每次编辑即时写入而非随最终的文档选择：操作者添加目录后、选文档前刷新，该路径仍会保住。之后每次列表调用都把它们作为参数带给宿主，因此答案由客户端持有、宿主保持只读。

第四步是声明项目编译服务器之处，也是向导除项目自身代码库之外唯一的写入。表单收集声明记录所持有的字段——服务器 ID、用户名、服务器 IP、是否记录源码版本，以及一次运行可选择的 recipes——而 OpenSSH 目标由后两者拼成而非手打：它是一个有语法的字符串，而操作者真正知道的是自己以谁的身份登录、要连哪台机器——而编译工程目录是"选"出来的而不是"打"出来的：操作者先连接，该步骤从登录目录开始列出机器上的内容——每次连接取多层，因此点击由已持有的内容作答，而不是每次都付一次往返——最终停留的那个路径就是被声明的东西。在开发机上手打的服务器路径正是最容易填错的一项——浏览用的共享路径与那台机器看到的路径是两个字符串——而验证 destination 可用的那次连接，也正是能展示那里有什么的同一次连接（每条 recipe 可选各自声明产物落在哪个目录——同一棵树的整编与局部编译产物位置不同）——并经 `ctx.yxspecRemote.declare` 提交，也就是 `remote_server_declare` 工具所用的同一个调用，因此向导里做的声明与智能体做的声明是同一份记录、同一种写法。每次写入后，该步骤从宿主读回清单，而不是把刚输入的内容追加到列表上，因此用同一个 id 重新声明会替换原有行，而不会把同一台服务器显示两次。前进只有一个控件：不声明服务器就继续、与已声明服务器后继续是同一个动作，文案跟随状态，而不是给出两个让操作者去找一个并不存在的差别的按钮。每一行用一个圆点报告最近一次连接测试的结论——尚未测试为灰色、服务器应答后为绿色、失败后为红色——观测到的平台或宿主自己给出的失败原因位于圆点之后，失败时直接显示出来，因为缺的是哪个目录正是操作者要处理的事；该行各带一个测试控件，声明落地后立刻自动测试一次，因此"添加好了，连得上吗"不需要第二次操作。状态是从宿主读回的而非组件自己持有的，所以刷新或换一个浏览器得到的答案相同。

<a id="understand-the-implementation"></a>
## 理解实现

<details>
<summary>实现细节——点击展开</summary>

本包是两半式插件：`src/index.ts` 是一个空的 `apply`，用于让它在宿主加载器名册中占位；浏览器半边经 `exports["./client"]` 发布，由该包自身的 `dsh.client` 声明发现。客户端入口为 Remote 载波以及两个命名空间键声明 `inject`——`remote.yxspec` 与 `remote.yxspecRemote` 由 Gateway 作为独立的 `remote.<命名空间>` 服务安装，而 Cordis 只允许插件读取它点过名的服务。源码注释记录了这里为何必须点名：漏掉一个不会在装载时响亮失败，因为读取会抛 `cannot get property without inject`，而这在该界面自身的加载器内会与"宿主确实未挂载"坍塌到同一条不可用分支。

分区注册到 `conversation.session.panel.section`，并在挂载时加载一次。它刻意不持有订阅：过期读数由下次挂载纠正，因为对一个只在智能体推进一步时才变化的表而言，实时订阅只会增加宿主到客户端的流量。向导注册到 `conversation.hero.frame` 且 `order: -100`，因此是最外层；在项目尚未完成引导期间，它替换而非包裹该 frame 的子节点——那些子节点是承载编辑器座位的滚动主体，所以不渲染它们就是这道门，既没有可重新启用的禁用输入框，也没有可能与之相悖的第二条代码路径。

进度经 `createSnapshotStore` 持久化，在同一份记录内按项目为键，保存时整体重写记录，因为存储形状是只读的，而标识符只在调用点才被解析。为项目命名是一次注入调用，而不是"先 create 再保存"：项目的 id 要等 create 应答才存在，而记录正是以该 id 为键，放在组件里做就意味着要往它自己那次渲染从未见过的标识符下写数据。该 seam 拿到宿主应答的项目，在其下同时写入 target 槽与该步骤的记录；当第一步是从一趟已记录的引导中再次进入时，它改名而不另建一个。第二步的列表直接读自被解析出的项目行而非本地草稿，因此在任何其他项目界面上的改动，这里同样可见。

规格步骤把自身的添加项留在本地 state 中，并镜像自已记录的答案，每当它们变化就重跑读取——该列表是读取的依赖项，因此往里添加一个目录会重跑调用，而不需要第二个专门重取的控件。被取消的挑选，或挑选了一个已在列表上的目录，不改动任何东西、也不重跑任何东西；被拒绝的 picker 渲染其消息，且不扰动检索。这些添加项由客户端而非宿主持有，因为它们属于某位操作者的一次检索，而非属于项目：它们不门控任何东西，没有其他界面读取它们，而存在宿主侧则会给持久状态引入第二条写入路径，去回答一个调用方本已持有的问题。

## 已知限制与延期工作

<a id="known-limitations-and-deferred-work"></a>

- **面板不能推进步骤** — 该分区按设计只读，因此推进流程始终是经宿主门禁的一次工具调用。想要 UI 按钮的部署没有受支持的路径，而加一个按钮会造出这套设计本就要消除的第二条不受控路径。
- **分区只加载一次，不刷新** — 它没有订阅或轮询支撑，因此智能体在面板打开期间推进的步骤要等重新挂载后才显示。
- **引导进度按浏览器而非按宿主** — 记录存在浏览器存储中并按项目为键，因此换一个浏览器或清空存储会再问一次操作者。
- **这道门依赖已确定的项目标识** — 向导在渲染时先解析本次引导自己的 target 记录，其次才回退到标准会话与工作区套件。项目已被删除的 target 是刻意不予采信的，于是引导退回目录规则，而当目录规则也无法指名项目时，向导会再次出现。
- **第一步的拒绝是重试而非回滚** — 被拒绝的 create 或 rename 会渲染其消息，并让该步骤保持打开、保留操作者已输入的名称；这里没有需要清理的半成品项目，因为 create 要么带回了 id，要么根本没发生。
- **缺少命名空间的部署会静默退化** — 未挂载的宿主与被拒绝的调用都渲染为不可用提示或空列表而非错误，这是刻意为之，但也意味着配置挂载有误的健康宿主看起来与不存在的宿主一样。
- **添加的检索目录不会校验其是否为目录** — picker 返回一个路径，该步骤记录下来；宿主随后遍历它，并把它报在 `searched` 中，即便那里什么都没有。一个根本不是目录的路径，或一个非绝对路径，贡献的是零候选而非错误，因此操作者的诊断依据是检索报告，而不是一次拒绝。
- **添加项按浏览器而非按宿主** — 与向导其余的进度一样，它们存在浏览器存储中并按项目为键，因此换一个浏览器会从项目自身的布局重新开始。
- **`ready` 不是一次探测** — 完成服务器步骤记录的是"问题被回答过"，而非"所声明的服务器可达"；向导不做探测。
- **文案有八种语言，流程自身文本没有** — 面板与向导已本地化，而模型看到的步骤契约与拒绝理由仍为固定中文散文。
